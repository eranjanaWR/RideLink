# Diagram-generation prompts

These prompts are optional sources for producing polished report graphics. Generated images must be checked against the Mermaid diagrams and current implementation before submission.

## A. Full system architecture diagram prompt

> Create a clean academic software-architecture diagram in a landscape layout for a university report. Title it “RideLink Backend Architecture”. Show one client area labeled “Client / Postman / Swagger” communicating through REST/JSON with four independently executable Java 21 Spring Boot microservices: Account Service on port 8081, Driver & Vehicle Service on port 8082, Ride Management Service on port 8083, and Fare & Payment Service on port 8084. Show Account Service registering users and issuing JWT Bearer tokens. Label user-facing protected calls “Authorization: Bearer JWT”, and make clear that Driver & Vehicle, Ride Management, and Fare & Payment independently validate Account Service JWTs. Show a trusted REST arrow from Ride Management to Driver & Vehicle labeled “eligible-driver search, availability synchronization, X-Internal-Service-Key”. Show another trusted REST arrow from Ride Management to Fare & Payment labeled “final fare create/reuse, payment create/reuse, X-Internal-Service-Key”. Connect each service only to its own separate MongoDB database: ridelink_account_db, ridelink_driver_db, ridelink_ride_db, and ridelink_fare_payment_db. Add a clear note: “No cross-service database access”. Use consistent service boxes, database-cylinder symbols, restrained blue/green/orange colors, readable labels, generous spacing, and professional typography. Do not include a frontend application, API gateway, Kafka, event bus, shared database, or unimplemented service.

## B. Git branch workflow diagram prompt

> Create a polished landscape Git workflow diagram suitable for a university software-engineering report. Show short-lived `feature/...`, `chore/...`, and `fix/...` branches flowing through pull requests into `dev`, then `dev` into `release`, `release` into `main`, and finally a `v1.0.0` tag on `main`. Include representative branch labels `feature/eranjana/driver-jwt-security`, `feature/eranjana/ride-jwt-security`, `feature/dineth/fare-payment-jwt-security`, `chore/eranjana/github-actions-ci`, and `chore/eranjana/final-postman-docs`. Show that Eranjana and Dineth use their own branch namespaces. Annotate pull-request gates with peer review: “Eranjana changes reviewed by Dineth” and “Dineth changes reviewed by Eranjana”. Use distinct but restrained colors for feature/chore/fix branches, integration branch, release branch, and main; include directional arrows, clear merge points, no commit hashes, and concise labels. The final visual should communicate the flow `feature/chore/fix → dev → release → main → v1.0.0` without decorative clutter.
